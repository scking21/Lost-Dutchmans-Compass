## Historical discovery route (not the primary judge start)

For the current primary route, use the desktop judge walkthrough above and the broader corridor workflow below. The original deployment represented by sanitized source `fb5c5d1` supplies desktop discovery evidence. Two subsequent local-resolution pilots stopped unresolved before ranking; the older app did not retain the issue detail needed to classify those failures. The newer successful run does not establish their causes.
1. Set a public destination city and a cultural favorite/category. Recommend places is the action for this legacy discovery route; the primary judge route is **Build a broader Mesa-area comparison**. Current scope and mode summaries stay visible; open **Scope, test modes and request limits** to change secondary options. Access, safety and historical truth require independent evidence.
2. Submit discovery only within an approved call budget. If `needs_input`, choose the intended provider identity. Otherwise inspect status; never substitute fabricated places on failure or interpret an empty result as proof no place exists.
3. Read the **resolved favorite and destination heading**: the actual resolved favorite, category and completed request’s destination. This is Compass’s query summary, not a Qloo causal explanation or personality inference. Rank reuses geography from earlier discovery; it does not recheck location.
4. Inspect returned place cards, addresses, raw affinity and provider positions. Broad discovery now defaults to explicitly unscoped results with a suitability warning. The optional local filter retains only session-reviewed catalogue matches; it never adds a recommendation. Open **Place evidence** for entity/type evidence and **Inspect source and request evidence** for the safe trace.
5. Shortlist, hide or restore locally. These actions make zero provider calls and do not supply a negative taste signal or change Qloo’s order/scores. The suggested next step changes from considering a shortlist to checking the venue’s own current visitor information. Shortlisting is not access verification, a booking or a generated itinerary.
6. Use **Edit your brief** to return to the favorite field. Changing inputs clears stale results. Explicitly change favorite/category to enable **Rerank retained places with changed taste**, subject to capacity. A shortlist restricts the retained set; otherwise all visible places are used. Changed destination requires fresh discovery.
7. Inspect official rank output, omitted IDs, prior/current positions and any query-level explanation. Do not compare numerical affinities across requests or infer individual behavior, access or safety. External factual checks are a separate task.

## Legacy two-place local-shortlist contract

- Use Mesa, then explicitly click **Resolve two local places · up to 4 calls**. Only the named museum and regional park are resolved; arbitrary provider queries cannot be supplied.
- Verify a matched ready state before clicking **Rank matched local places · up to 7 calls**. A failure or mismatched identity stops with no automatic retry. When only the second place is ambiguous and exactly one candidate matches all fixed catalogue identity facts, **Confirm exact identity · up to 1 call** offers a separate, one-use identity verification; it never auto-selects or auto-ranks. A sole candidate is not a taste comparison.
- Resolution IDs are stored only in session-owned, 15-minute server memory. No provider mapping or response-derived fixture is bundled in the public source.
- Ranked cards automatically use the reviewed local scope; returned name/address changes fail closed. Omitted results remain unranked, and initial catalogue ordering is not misrepresented as prior Qloo ranking.
- Resolution, optional confirmation and ranking are individually bounded by four, one and seven provider dispatches. Judging mode has no shared lifetime testing ceiling. Only one live submission runs at a time; a busy response uses no provider calls and preserves the context for an explicit manual retry. Four submissions per session/socket per minute and sixty per socket per minute limit load. Provider auth errors pause execution; rate limits honor Retry-After without automatic retries. Provider account allowance is unknown.

## Broader corridor workflow for a browser-capable agent

Use only visible controls and returned states. Start with a concrete visitor goal and state which choices come from the agent versus Qloo. The public UI’s “Build a broader Mesa-area comparison” section supports this bounded sequence:

1. Choose an addressed catalogue venue; click “Resolve selected place” (at most two dispatches). On `curated_choice`, observe its name, address and type. Choose the matching option and click “Confirm selected identity” (one dispatch). `curated_confirmed` adds a session-owned identity. Repeat explicitly for two to four places; do not substitute an unmatched venue without a new user decision or a predeclared protocol allowing it.
2. Resolve a cultural favorite and explicitly choose/confirm its identity using the same state sequence. Up to two confirmed favorites may be selected. “None of these match” returns to editing with no call. A book author/year is not a resolution guarantee.
3. Select one or both confirmed-favorite checkboxes and click “Rank confirmed choices.” This is one official rank workflow, bounded by option count + signal count + one insights request, maximum seven dispatches. No model credentials, extra provider or unrestricted query proxy is introduced.
4. Inspect `curated_results`: complete returned positions, omitted catalogue IDs, confirmed signal names, bounded actual provider detail when returned, and audit dispatch counts/input hash. Make any local shortlist choice as the agent’s own decision, not a Qloo causal explanation. Local shortlisting makes no calls.
5. For counterfactual comparison, keep the place set fixed and explicitly change selected confirmed favorites before another rank. Report observed ordinal changes, coverage and failures without treating raw scores across calls as comparable or proving visitor benefit.

No action automatically follows another. `busy`/rate pauses require an explicit later action; authentication and provider stops halt the run. Four submissions per minute and one active live request apply across this app. Session identity expiry requires fresh resolution; it is not permission to retry a frozen evaluation. Browser-agent evidence must describe actual goal-led decisions from observed states, not relabel a click script as autonomous behavior. Judges determine whether the demonstrated workflow satisfies eligibility.

## Authentication and interruption recovery

Check the readiness message before a live action. Provider authentication errors pause the server process; browser refresh does not clear that pause. The owner must check/correct the existing server credential and restart the process, then users reload and explicitly resolve/confirm identities again because server memory is lost. See [server configuration and recovery](../README.md#server-configuration-and-recovery). Busy/rate pauses and expired confirmations need explicit later actions; they never authorize automatic retries, substitutes or reruns of a frozen comparison. A nonempty configured key is not proof of provider validity or remaining allowance.
